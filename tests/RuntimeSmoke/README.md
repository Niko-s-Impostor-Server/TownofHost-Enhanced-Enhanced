# Local runtime smoke helper

This separate test-only BepInEx plugin is excluded from TOHE compilation and has no deployment target. It accepts exactly `snapshot`, `capture`, `freeplay`, `locallobby`, `gui_local`, `gui_lobby`, `lobby_welcome`, `gui_tasks`, `gui_roles`, `leave`, `local_join`, `local_start`, `local_leave`, `local_chat_watch`, `local_cmd_id`, `local_task`, `local_meeting`, `local_meeting_request`, `local_skip`, `local_prepare_abilities`, `local_phantom`, `local_ability_meeting`, `local_judge`, `nikocn_host`, `nikocn_join`, `online_leave`, and `online_start`; arguments and other commands are rejected. It has no reflection invocation, login, account modification, arbitrary endpoint, or desktop automation interface. Online commands are restricted to the existing NikoCN region and a local ticket for the authorized private test room.

Build the main plugin first, then build this project with the same configuration:

```powershell
dotnet build .\TOHE.csproj -c Release '-p:LocalAmongUsPath=D:\Game\20260818\Itch' '-p:AmongUs='
dotnet build .\tests\RuntimeSmoke\RuntimeSmoke.csproj -c Release '-p:LocalAmongUsPath=D:\Game\20260818\Itch'
```

To reference a different existing main-plugin build, supply `-p:TOHEAssemblyPath=<absolute path to TOHE.dll>`. The helper uses the actual installation's core and generated interop assemblies. References are not copied into its output.

For a manually authorized test installation, the DLL list is:

- `TOHE.dll`: the matching main-plugin build, already installed for the test.
- `TOHEE.RuntimeSmoke.dll`: `tests/RuntimeSmoke/bin/Release/net6.0/TOHEE.RuntimeSmoke.dll`, copied separately to `BepInEx/plugins` only during testing.

Do not distribute this helper in product builds. Do not copy core/interop DLLs or its `.deps.json` over the game. This project does not install or launch anything. Use one helper instance per game directory to avoid sharing command/output files.

Once the manually started game has loaded the helper, write one fixed command to `.tohee-smoke/command.txt`. For an atomic command handoff:

```powershell
$smokeDirectory = 'D:\Game\20260818\Itch\.tohee-smoke'
New-Item -ItemType Directory -Path $smokeDirectory -Force | Out-Null
Set-Content -LiteralPath "$smokeDirectory\command.tmp" -Value 'snapshot' -Encoding utf8
Move-Item -LiteralPath "$smokeDirectory\command.tmp" -Destination "$smokeDirectory\command.txt" -Force
```

Replace only the literal command with one of the documented fixed commands. The helper claims and deletes each command once. `status.json` records command completion/rejection/failure/timeout; `snapshot.json` records scene, mod presence, mode/state, player count, host status, and known GUI component object names. A fixed `TOHEECredentials` diagnostic additionally records positions, camera screen coordinates, rect dimensions, font asset name/size, renderer status, enabled/active state; its text is never read. Error/Fatal log severities are counted without retaining messages. No player/account identifiers are written. `capture` writes only `.tohee-smoke/capture.png` using Unity's ScreenCapture API and checks both the PNG signature and final IEND chunk. A screenshot contains visible game content; treat it as a local test artifact.

`freeplay` requires a disconnected client in `MainMenu` and a loaded `FreeplayPopover` whose native host button is configured as `FreePlay`. It opens the native game-mode menu, activates the popover, calls `Show()`, checks the host button is active, then calls `PlayMap(MapNames.Skeld)`. The verified native path uses a loopback-only freeplay server and the Tutorial scene. Completion requires Tutorial, FreePlay mode, local player, and ship.

`locallobby` requires a disconnected client in `MainMenu` or `MatchMaking`. From MainMenu it calls `OpenGameModeMenu()` and only the native `SceneChanger` targeting `MatchMaking`. It waits for the loaded `HostLocalGameButton` configured as `LocalGame`, activates its scene ancestry if needed, and calls its native `OnClick()` once. That native path connects the client to `127.0.0.1:22023` and uses `OnlineGame` as the local lobby scene. **The native LocalGame server listens on all IPv4 interfaces for LAN play**, unlike FreePlay's loopback-only listener. No online matchmaking, authentication changes, external server endpoint, or automatic join invitations are performed. Completion requires LocalGame mode, local host, Joined state, local player/data, GameStartManager, and no ShipStatus.

`leave` calls native `AmongUsClient.ExitGame` only for FreePlay or a LocalGame host session started by this helper. It stops this helper's LocalGame server, then waits for a disconnected native menu: MainMenu for FreePlay, MatchMaking for LocalGame. An unrelated or online multiplayer session is rejected. From a disconnected native menu it succeeds immediately. Each operation has one 8 second total timeout across scene transitions and connection.

`gui_local` requires a ready LocalGame lobby started by this helper, with settings closed and no ship. It opens settings through native `GameStartManager.ClickEdit()`. It exercises interruption by switching SystemSettings → vanilla settings → SystemSettings, then visits only mod tabs with a visible native cloned tab button for the current mode. It validates one menu per definition tab, complete unique definition/control and header mappings, hidden-control exclusion, controller selection/back button, and active owned up/down navigation. Existing role help icons are checked before and after three `StringOption.Initialize()` calls. It closes settings, creates another owner and closes during its fresh SystemSettings build, then opens a third owner and compares complete counts with the first. Each close must destroy the owner and clear all three registries. It changes no option values. Output is `.tohee-smoke/gui-local.json`, with numeric counts, fixed check labels, and error-severity deltas. Any observed Error/Fatal during this sequence fails it; the 8 second total timeout also fails, never passes an incomplete build. Settings are closed after success, failure, or timeout when the test still owns the menu. This is structural lifecycle/navigation coverage; it does not prove visual layout or online multiplayer behavior.

`gui_lobby` requires this helper's owned host lobby at exactly `127.0.0.1:22023`, GameId 32, Joined state, exactly one player, a visible standalone preview, closed native chat/settings, and an empty system-message queue. It observes the existing preview across `OptionShower.Next()` and a return to the original page, opens/closes chat through native `ChatController.Toggle()`, and requires the same single live TMP object to hide/restore. Its nonblocking observer has an eight-second total limit. It restores the original page and requests native chat close on completion/failure/timeout while the session remains owned. `gui_local` additionally checks the preview hides over loaded settings tabs and restores after each native settings close.

`lobby_welcome` has the same single-player restrictions and accepts only an existing template with exactly one `welcome` entry using the known shipped Chinese title, either the old missing-`>` form or the corrected form. Customized titles are rejected without being changed. It invokes the actual public `TemplateManager.SendTemplate("welcome", byte.MaxValue)` once; the public API retains its ordinary template initialization behavior. It opens native chat, observes a newly displayed welcome bubble, compares only the fixed visible title prefix, rejects exposed raw `<color` markup, measures world-space native title/body text bounds for overlap, and checks the player's display name is restored. Raw names and template/chat text are never serialized. It closes chat after observation and restores the original page. It uses the normal message queue/cooldown and does not manufacture packets or reset timers.

Both commands write `.tohee-smoke/lobby-ui.json` with fixed check labels, structural booleans, font/rect/bounds metrics, and error-severity deltas. `snapshot` includes the current `lobby_layout` metrics. The helper requests `lobby-preview-first.png`, `lobby-preview-next.png`, and `lobby-welcome.png` through native `ScreenCapture`; these auxiliary captures are not independently validated PNG completion checks, so inspect them separately. A successful observer proves the local native UI states it sampled, not visual readability, keyboard input, all languages/pages/resolutions, or multiplayer behavior.

`gui_tasks` requires Tutorial/FreePlay, ship and native role data, a TOHE player-state entry with a restorable main role, and no open minigame. It follows the verified `SystemConsole.Use` instantiation path for the loaded TaskAdder prefab (without requiring input or proximity). It opens the TOHE role folder, validates all role buttons and controller registrations, selects the fixed CrewmateTOHE → EngineerTOHE → CrewmateTOHE sequence using native `TaskAddButton.AddTask()`, and checks native/custom role data, OnAdd ownership/enable state, old role instance removal, unused old static role disable state, and exclusive main-role checkmarks after multiple Updates. Native local/dummy task counts are recorded and must remain unchanged. It returns to root, reopens the folder, verifies old buttons were destroyed and counts remained stable, restores the original role through its button, then closes and repeats with a different TaskAdder owner. Output is `.tohee-smoke/gui-tasks.json`. It never changes a role in an online/local multiplayer lobby. Timeout/failure cleanup restores the original role only when a complete live role folder is still available; otherwise issue `leave` and create fresh FreePlay before continuing. A rejected command means the required product initialization has not completed and is not test success.

`gui_roles` uses native TaskAdder navigation to select 25 fixed representative main roles. Each must pass native/custom role agreement, old role cleanup, at least five actual HUD updates, and a task-panel first line matching both the text source and TMP's parsed display across two frames. Taskless roles must retain their description. Each selection has a two-second observation limit and the complete sequence has 25 seconds. The original role is restored, and `gui-roles.json` records counts and `skill_functionality_tested=false`; activation does not prove role abilities.

The first `gui_tasks` owner also visits the native crew/impostor role folders and checks that Detective, Viper and Judge are absent. Three inactive copies of the actual native RoleButton prefab call the fixed `AddTask` handler with those actual role prototypes; rejection must leave native/custom role instances, tasks and controller/UI state unchanged across updates. The temporary copies are then destroyed. Visible native Engineer and Crewmate buttons must still switch correctly before original-role restoration. No new native ability is claimed as supported by these checks.

`local_join` uses the loaded native LAN JoinGameButton for the fixed `127.0.0.1:22023` host. It checks two or three players and remembers the resulting native session. `local_start` requires this helper's host and two or three players, freezes that count for the entire start observation, temporarily enables the normal NoGameEnd option without saving, and calls native BeginGame once. It observes all players' role data, intro completion, tasks and local movement. This permits testing a two-player/all-crewmate configuration or a three-player room containing two mod clients and one independently operated true vanilla client without an immediate win. Native intro animation gets a 15-second observer; other stages get eight seconds and the whole command gets 30 seconds. `local_leave` restores the original option and exits the remembered session; the host also stops its owned LAN server. Leave clients before the host. These operations never alter authentication or server protections. Existing task, meeting and ability commands still require exactly two players.

`snapshot` also reads the native `CurrentModRegistration.ModRegistrationGuidString`; this diagnostic never assigns registration data. The GUID identifies the mod version and is not a player/account identifier.

`local_chat_watch` and `local_cmd_id` require the remembered helper-owned local session at exactly `127.0.0.1:22023`, GameId 32, two or three players, and Joined or Started state. Both attach a fixed set of Harmony observers for eight seconds, recheck session/client/local-player identity and the frozen player count on every Tick, then remove all observers. Observers only count native chat calls, fixed `/cmd id` receipt/dispatch, private reply targeting and replay attempts; they never modify arguments or results and retain no chat text, names, account IDs, player IDs, pointers or RPC payloads. The output is `.tohee-smoke/private-chat.json` and the `private_chat` object in a fresh snapshot. Failure or ownership loss removes the observers as well.

For the fixed chat scenario, enable the normal vote-command option beforehand through the product's settings, keep free-chat input empty, and let the native chat cooldown naturally reach three seconds. Start `local_chat_watch` on the host and, optionally, any other helper-owned mod client, then promptly issue `local_cmd_id` on the owned mod non-host. That command inserts only the fixed `/cmd id` literal through native `TextBoxTMP.SetText()` and calls native `ChatController.SendChat()` once. It never resets cooldown or constructs a packet. The sender must observe exactly one executed native UI send, one native RpcSendChat call, one reliable native SendChat RPC targeted at HostId, and one remote native AddChat whose text starts with the fixed translated PlayerIdList heading; other chat routes fail. Only that heading is compared, across native supported languages, and no response body is retained. The host watcher must independently observe exactly one received and consumed envelope, one `/id` core dispatch and one reply targeted at the command sender. An attempted `/cmd` or fixed `/id` AddChat, any replay invocation during the window, or a broadcast reply during dispatch fails. Native AddChat execution and remote-source AddChat counts are also reported without saving response text.

The sender report explicitly requires a separate host report to prove execution. A watcher on another mod client supplies an additional bounded observation, while a true vanilla client must be operated and inspected independently with no helper/mod DLLs installed. The helper does not prove the true vanilla client's screen, response content, delayed behavior beyond eight seconds, or the online server's routing. Capture visible UI separately for those claims. A watcher that receives no fixed command on the host fails; passive non-host watchers report only their observed eight-second window.

Start the host watcher and send the client command within the same eight-second window; `started_utc`/`ended_utc` and local monotonic times support alignment. Passive watchers install only the fixed receive/core/reply/replay/AddChat observers; sender hooks are installed only for `local_cmd_id`. Failures retain the fixed target label, phase and up to eight nested exception types with fixed safe message categories. Raw exception messages, stack traces and arguments are omitted. Cleanup disables observation first, then removes this helper's patches separately per fixed target. Cleanup failures have their own diagnostic array and never replace an earlier setup/observation failure; a previously successful observation becomes failed if removal is incomplete. Any remaining target is inert and a new chat scenario is rejected until that test process is restarted. This is diagnostic failure, never evidence that the chat check passed.

`local_meeting` requires the owned LocalGame non-host, two alive players, and an emergency console within native permitted use range. It calls SystemConsole.Use and EmergencyMinigame.CallMeeting, retaining native cooldown, crisis and remaining-meeting checks. Once voting is available, run `local_skip` on both instances. Each clicks the normal Skip and Confirm buttons, waits for the native vote animation to show exactly two Skip icons and zero player votes, and observes return to gameplay with nobody ejected. LocalGame requires its host's normal Proceed button; only the host invokes that button. Commands have eight-second stages, 15-second meeting/exit animation observations, and a 30-second total limit. They never move a player, modify voting settings or send fabricated RPCs.

`local_meeting_request` requires the same owned non-host LocalGame context and an ordinary CrewmateTOHE. It calls the native `CmdReportDeadBody(null)` once after cooldown, crisis and remaining-count checks. It covers the client-to-host meeting request and subsequent meeting lifecycle, not console proximity, minigame UI or emergency-count consumption. Use `local_skip` on both clients afterward as above.

`local_task` requires the owned LocalGame non-host with an ordinary CrewmateTOHE, two alive players, and no open meeting/minigame. It selects an existing uncompleted one-step native task and calls `NormalPlayerTask.NextStep()` once, the callback used by normal minigames. It observes the installed completion flag and exactly one increment in personal/shared progress, without changing totals. Take a fresh host `snapshot` to verify the network result separately. It does not test the task minigame's input or visuals and never submits an invented task ID. Its observation timeout is eight seconds.

The four ability commands are restricted to the remembered helper-owned `127.0.0.1:22023`, GameId 32, normal LocalGame session with exactly two alive players. They are never available online. Each action uses nonblocking Tick observers with eight-second stages and a 30-second total limit; inability to observe a required result is failure or timeout, never success. They use public TOHE role APIs and generated native interop members, and invoke no internal meeting-protocol method.

1. In the ready host lobby, run `local_prepare_abilities`. It requires the remote player's known matching mod version/fork, settings closed, automatic start/rehost disabled, and GM disabled. It backs up the current preset's Keeper/Disperser spawn/count options and both existing fixed role selections, then uses unsaved options (100 percent, one each) and the ordinary `RoleAssign.SetRoles` selection path to prepare host Keeper and remote Disperser. It records the original lobby kill cooldown. `local_start` retains its existing native BeginGame/intro sequence and additionally verifies the exact custom/native roles, matching remote version, and original kill cooldown in `Main.RealOptionsData`. A changed preparation is rejected before BeginGame. `local_leave`/`leave` restores these options and selections before exiting; ownership loss also attempts unsaved restoration. A restoration failure remains visible and can be retried with `local_leave`. No disk config is saved.
2. After the existing start succeeds and the native cooldown naturally expires, run `local_phantom` on the non-host. It requires real native Phantom role data, Disperser, ordinary task gameplay, visible/non-fading state, no role animation, and both players allowing native teleport. It invokes `PhantomRole.UseAbility()` exactly once, the actual role input handler. Success requires both players to move more than 0.5 units to a real native vent teleport destination, a started native cooldown, and at least five observed frames plus 0.75 seconds of unchanged visibility/alpha, no fading or role animations, and unchanged native/mod/shared tasks and emergency counts. It does not move players or reset cooldown. If a random destination is indistinguishable from the original position, the scenario times out rather than claiming teleport success.
3. Once native cooldown/crisis/emergency conditions permit, run `local_ability_meeting` on the host Keeper. It calls its own `CmdReportDeadBody(null)` once and observes a ready native meeting. Tasks and the remote emergency count must remain unchanged; the native caller's `StartMeeting(null)` must consume exactly one emergency. The observer permits that one expected transition while opening and requires it before declaring the meeting ready. It then rebases only the caller's emergency baseline, so subsequent Judge/skip checks strictly preserve the post-meeting count. This tests the native request path and count consumption, not console proximity or minigame input.
4. When discussion has ended and voting becomes available, run `local_judge` on that host. It waits for the temporary real native Judge presentation, calls the unique remote `PlayerVoteArea.Select()`, verifies the expanded active native Judge button, and invokes its bound `JudgeOverruleVote()` handler once. Success requires Keeper's publicly rendered remaining-use progress to decrease by exactly one, while both ordinary vote states, tasks, emergency counts, and custom role instances remain unchanged; the native Judge queue must stay empty and `wasOverruled` false. Then run existing `local_skip` on both instances to cast ordinary Skip votes. Its completion additionally verifies restoration of the native Crewmate/Phantom role bases and preserved task/custom-role state for this scenario.

The `abilities` snapshot reports fixed stage labels, sanitized counts/booleans/cooldowns, and pending option restoration. `baseline_comparison_failure` distinguishes unexpected emergency counts, task totals/progress, replaced native task data/objects, and changed custom role instances. Emergency/shared-task before/observed counts and the expected native consumption/rebase flags support diagnosis without writing player IDs, names, accounts, task IDs, native pointers, or raw progress text. Take fresh snapshots on both clients to compare network observations. Tick sampling proves only the recorded client observations; compile success alone does not establish native UI availability, host acceptance, teleports, meeting readiness, or multiplayer skill success.

Online testing is manually initiated only after the offline GUI checks. Use at most three separately installed Itch instances; the native `Constants.GetPlatformType()` must identify StandaloneItch, and other platforms are rejected. Each instance needs its own game directory and working directory for BepInEx/config/logs, TOHE-DATA, and `.tohee-smoke`. Copying game directories does not isolate the same Windows user's Unity `player.amogus`, `settings.amogus`, `regionInfo.json`, `persLog.log`, or EOS cache. Do not copy or modify login files to manufacture another identity. Native account/session or Nmpostor duplicate-connection refusals are test stop conditions, not reasons to change authentication or server protection.

`nikocn_host` requires a disconnected MainMenu, an already completed EOS login with `LoggedIn` account status, and normal online permission. It refuses configured automatic start/rehost and public rehost state. It selects exactly the existing unique `Niko233(CN2)` HTTP region, with one non-DTLS server whose endpoint is `https://au-cn.netease.me:443/`, and no target-server override. It never adds or edits a region. Native MainMenu → CreateGameOptions opens the normal creation UI first. After its overlay is ready, `OpenServerDropdown()` opens the initialized native dropdown and its fixed `ServerDropdown.ChooseOption(existingRegion)` handler selects/saves the region and closes the dropdown. That original private handler is exposed by generated IL2CPP interop; no reflection or direct server-field assignment is used. The normal confirmation → `Confirm()` then performs the game's own permission and matchmaking flow. Existing game options are retained. Completion requires a private host lobby, player/data, lobby manager, and no ship. Only then it atomically writes `.tohee-smoke/.test-room.json`, containing the native GameId/RoomCode, CreatedUtc, fixed TestMarker, and Region. No account/token data is stored. The helper remembers the original region for a later `online_leave`.

`nikocn_join` reads only `.tohee-smoke/.test-room.json`, copied manually from this test's successful host into the client instance. It rejects missing/malformed/oversized tickets, wrong marker/region, inconsistent GameId/code, future timestamps, and tickets older than 30 minutes. It first uses the same normal CreateGameOptions/ServerDropdown path to select the existing CN region, then calls native `CreateGameOptions.Close()` and waits for CoHide → GoBackCreateGame → OpenOnlineMenu/ResetScreen to make the creation page inactive. Only then does it open the normal native EnterCode UI: the menu-selected TextBox receives the exact ticket code, `LookForGame()` performs native permissions/lookup, and `ClickJoin()` runs once only when its original native UI button becomes enabled. Public UnityEvent metadata identifies that fixed ClickJoin binding; no event metadata or arbitrary method is invoked. It does not query public room lists, accept command arguments, or construct server connections. The ticket records the private room at creation; keep that room private throughout the test, because native GameListing has no public/private flag before joining. Completion checks the matching GameId, private client lobby, and at most three players.

`online_start` requires this helper's remembered private host lobby, two or three connected players, settings closed, completed login, and automatic start/rehost disabled. It calls the existing `GameStartManager.BeginGame()` UI entry once, including the installed TOHE patch and normal countdown. It succeeds only after Started, ship, native role, intro completion, and local CanMove. It performs no movement, meeting, vote, direct RPC, or role mutation.

`online_leave` refuses connected rooms not remembered by this helper. It exits the remembered room using native `AmongUsClient.ExitGame(ExitGame)`, waits for a disconnected MainMenu, and, if the selected region differs, restores the original existing region through the same normal CreateGameOptions/ServerDropdown UI, then closes the creation page through its native Close/GoBack chain. If the original region is already selected, no reselection is needed. A region restore that needs the creation UI also requires normal online permission; if login has expired it fails and retains the pending restore instead of changing login state. Clients should leave before the host. It can also restore the region after a failed attempt that returned to disconnected MainMenu. A restart loses helper ownership; it cannot claim an already connected room. A native creation that completes only after the observation timeout is also not retrospectively claimed, and must be handled through normal UI.

The snapshot's `online` object reports readiness, region match, private/owned-room booleans, lobby/ship/movement readiness, phase, and fixed result/disconnect labels. It outputs no account identifiers or authentication material. Poll `status.json` until `state` is `succeeded`, `failed`, `rejected`, or `timed_out`. Offline operations and disk work retain an 8 second reporting timeout; online phases have an 8 second observation limit and each online command has a 20 second total limit, with no automatic retry. Timeout stops future helper actions, but does not cancel the game's native coroutine or an already queued atomic disk write. Unity APIs run on the main thread; command/output disk work is performed in tasks, and Update never waits for an incomplete task. Compilation does not prove native UI hierarchy, authentication, room creation/join, or live multiplayer success. This test plugin must not be packaged with product releases.
