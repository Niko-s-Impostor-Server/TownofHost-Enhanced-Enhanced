# TOHE RPC 123

所有 TOHE 自定义消息通过原版 `IGameDataMessage` 广播队列发送。`TOHERpcMessage`
是唯一注册到 IL2CPP 的具体类，继承 `BaseGameDataMessage`；现有消息的载荷适配器
`CustomRpcPayloadMessage` 继承它。未复制 upstream 的自定义打包器或 RateLimit 逻辑。

原版 `BaseRpcMessage` 只是发送编码基类，没有接收注册表。接收仍由
`PlayerControl.HandleRpc` 的 Prefix 处理。

| 字段 | 格式 |
| --- | --- |
| RPC 对象 | 本地发送者的 `PlayerControl.NetId`，原版 packed uint |
| 外层 RPC | byte `123` |
| 收件人 | signed int32 OwnerId/ClientId；`-1` 表示全体 |
| 内层 RPC | 固定 4 字节 uint32 `CustomRPC`，不是 packed 编码 |
| 载荷 | 对应消息现有字段 |

外层始终广播；只有目标模组客户端与房主进入业务处理。收件人字段不提供隐私隔离。
权限按**内层 ID**检查，房主观察发给他人的消息时不播放收件人的声音、闪屏或弹窗。
发送方不自动本地回环，原有本地应用逻辑仍只执行一次。

新增消息可使用 `CustomRpcTransport.Send(id, writer => { ... }, target)`。旧消息调用
`Start` / `Finish`；`Finish` 在入队前复制载荷并回收 writer，然后调用原版打包发送，
保持旧 Immediately 调用与原生结束游戏消息之间的顺序。离开/加入房间释放未完成 builder。
不得保留已 Finish 的 writer，也不得从序列化回调再次发送消息。

接收拒绝短头、未知内层 ID、非法负 target、对象归属不一致和非房主的房主专用消息。
业务解析异常不会中止原版接收循环。`HandleRpc` 没有连接发送者参数；客户端的
OwnerId/Character 一致性检查不是连接身份认证，实际连接所有权由服务端验证。

这是不兼容的协议迁移：只读取 `int32 target + uint32 innerId` 的 8 字节头，
不兼容旧的裸 CustomRPC 或一字节内层编号。`123=SetFriendCode` 是内层消息编号，
必须以 uint32 封装在外层 byte 123 中。不要在同一模组房间混用旧 DLL。
以后新增 `CustomRPC` 直接在枚举末尾 Append，不在中间插入或复用编号；不增加旧协议兼容分支。
本次协议更新显示版本为 `2.1.1-au20260818.3`，也会改变已有版本派生的 Mod GUID。

后续 `.4` 修复在枚举末尾追加 `SyncExileText = 190`（仍为 uint32），只接受房主
发出的会议驱逐文本。载荷绑定房间、会议和玩家，具体生命周期见
[exile-text-lifecycle.md](exile-text-lifecycle.md)。因此 `.3` 与 `.4` 客户端应分别使用匹配构建。

离线验证：`tests/RpcTransport` 验证编码、载荷不可变、writer 租约与回收；
`tests/RpcReceiver` 链接生产入口验证收件人、权限和异常边界。它们不能证明 IL2CPP
虚调用、实际网络交付或服务端接纳；这些必须另外进行实机测试。
