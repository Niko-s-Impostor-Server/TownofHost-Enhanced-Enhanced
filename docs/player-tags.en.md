# Host-local player tags

Hosts use `TOHE-DATA/Tags/<friend code>.txt` to configure local player tags, permissions, and GM status. Tags appear before player names, and other players see them through name updates sent by the host. `TOHE-DATA/tags.txt` is only a lower-priority cosmetic tag fallback; it does not set permissions or GM status. These files are stored only on the host's device.

This is a deliberate behavior change: `TOHE-DATA/Moderators.txt` and `TOHE-DATA/VIP-List.txt` are no longer read and no longer grant or display MOD/VIP identities. The associated list options no longer appear in the interface, and the `/modcolor` and `/vipcolor` commands have been removed. Old MOD/VIP raw-color files do not grant identities or permissions. `MOD_TAGS` and `VIP_TAGS` are now ordinary folder names that can hold structured player configurations. Old configuration is not migrated automatically, and existing files are not deleted automatically. To retain local permissions or GM settings for a player, enter them manually in that player's `<friend code>.txt`. Built-in developer tags, including DevUser, still display, and the six-digit raw-color format in `Tags/SPONSOR_TAGS/<friend code>.txt` still overrides DevUser's built-in tag color.

## TOHE per-player TXT: tags and permissions

When the mod starts, it creates three templates in the `TOHE-DATA/Tags` root directory. Existing templates are not overwritten. On desktop, the path is relative to the game's working directory; on Android, per-player files are under the app's persistent data directory. These are examples to copy; the template files themselves do not match players or grant permissions:

| Template | Initial fields |
| --- | --- |
| `Tag_Template.txt` | `TagName` is empty, `TagColor: FFFF00`, `PermissionLevel: 0`, and all boolean fields are `false` |
| `Moderator_Template.txt` | `TagName: Moderator`, `TagColor: 8BBEE0`, `PermissionLevel: 5`, and all boolean fields are `false` |
| `VIP_Template.txt` | `TagName: VIP`, `TagColor: FFFF00`, `PermissionLevel: 1`, and all boolean fields are `false` |

Copy the template you want, rename the copy to the player's full friend code plus `.txt`, and place it in the `Tags` root or an immediate subdirectory (one level only). For example, copy `Moderator_Template.txt` to `TOHE-DATA/Tags/moderators/sampleuser#1234.txt`, or copy `VIP_Template.txt` to `TOHE-DATA/Tags/vips/sampleuser#1234.txt`, then edit the fields as needed. Levels are cumulative, so the Moderator template's level 5 includes lower-level permissions such as `/start`; lower `PermissionLevel` if those permissions are not needed. A template file itself grants no permissions; only a player configuration file named for a friend code takes effect.

```text
TagName:
TagColor: FFFF00
PermissionLevel: 0
SayCommandAccess: false
EndCommandAccess: false
ExecuteCommandAccess: false
AssignGameMaster: false
```

Do not include `#` in `TagColor`; a six-digit hexadecimal color sets a solid color. When the gradient-tag option is enabled, you can also specify two colors, such as `33CCFF FF99CC`. `TagColor` can be left empty to use formatting in `TagName` on its own. `TagName` supports color, size, and font markup, for example `<color=#FF0000>R</color><size=150%>ain</size>bow`. When **Enable Gradient Tags** is on, this rich-text markup is kept; when it is off, the markup is stripped while its visible text remains. An invalid `TagColor` falls back to yellow. To put a space between the tag and the name, leave a trailing space at the end of `TagName`.

## Use the MAUL tag generator

Use the [MAUL tag generator](https://moddedamong.us/tags.html) to create a TOHEE configuration: select `TONE/TOHE:E`, enter the player's full friend code, download the complete `.txt` configuration, and place it in the `Tags` root or a regular immediate subdirectory. The page's “Copy generated tag” button copies only the tag markup for `TagName`, not the full permissions configuration. The generator's gradient style puts `TMP` markup in `TagName` and leaves `TagColor` empty; its solid-color style fills `TagColor`. Enable **Enable Gradient Tags** to preserve inline color, size, and font markup; when disabled, the markup is stripped while the visible text remains. If you manually set a two-color gradient in `TagColor` alongside embedded colors in `TagName`, the automatic gradient recolors the visible text. Leave `TagColor` empty to preserve the embedded colors exactly. Boolean fields generated by the site may use `y`/`n`; both are accepted.

| `PermissionLevel` | Grants |
| --- | --- |
| 0 | Grants no permission-level management commands |
| 1 | Use `/rn` to rename yourself and `/color` to change your color in the lobby |
| 2 | Adds `/warn`, `/mid` for the player list, `/me <ID>` for another player's information, and requesting `/fix` for other players. `/id` for the player ID list is also available, but level 0–1 players can use it when the `EnableVoteCommand` option is on |
| 3 | Adds `/start` in the lobby |
| 4 | Adds `/kick` |
| 5 | Adds `/ban` (a reason is required) |

Permission levels are cumulative. `/me` without an ID shows your own information; `/me <ID>` requires level 2 to view another player's information. `/warn`, `/kick`, and `/ban` remain subject to target protections and host restrictions, so they cannot be used on every target. `/fix` remains subject to its target validity checks. Host permissions, built-in developer permissions, and game options allowing everyone to rename or change color still apply independently.

`SayCommandAccess`, `EndCommandAccess`, and `ExecuteCommandAccess` independently grant `/say`, `/end`, and `/exe`, respectively. `AssignGameMaster` assigns GM status only and **does not** automatically grant management commands. GM status and permission level are separate. These fields accept `true`, `yes`, `y`, `t`, and `1`; other values, including generator output `n`, are treated as disabled. Player permissions granted by local files come only from per-player TXT files. Neither tag text nor `tags.txt` can grant permissions.

Per-player TXT files can be placed in the `Tags` root or any immediate subdirectory (one level only), such as `Tags/moderators/<friend code>.txt`, `Tags/vips/<friend code>.txt`, `Tags/MOD_TAGS/<friend code>.txt`, `Tags/VIP_TAGS/<friend code>.txt`, or `Tags/SPONSOR_TAGS/<friend code>.txt`. Folder names are only for organization; they do not determine a player's tag, identity, or permissions. Those are determined by the file fields. A valid structured configuration must contain at least one recognized field: `TagName`, `TagColor`, `PermissionLevel`, `SayCommandAccess`, `EndCommandAccess`, `ExecuteCommandAccess`, or `AssignGameMaster`. Old raw-color files in `MOD_TAGS` and `VIP_TAGS` are not structured player configurations, do not create MOD/VIP identities or grant permissions, and do not mask another valid file for the same friend code. When valid files for the same friend code exist in multiple locations, all immediate subdirectories take precedence over the root; subdirectories are checked alphabetically, and the first valid match takes precedence. Matching uses the full friend code. In `SPONSOR_TAGS`, a file containing exactly a six-digit hexadecimal color remains an override for DevUser's built-in tag color; it is not treated as a structured player configuration and does not make an ordinary player a sponsor.

Individual configuration files larger than 16 KiB are not read.

## DevUser built-in tag color override

Raw-color files in `SPONSOR_TAGS` override DevUser's built-in tag color; this legacy color format cannot create a tag, add an identity, or grant permissions. The directory can also hold structured `<friend code>.txt` player configurations, just like other immediate subdirectories. Its name does not determine permissions or identity. Create the directory manually if it does not exist. The path below is relative to the host's game working directory.

| Color file | Conditions | Default color |
| --- | --- | --- |
| `TOHE-DATA/Tags/SPONSOR_TAGS/<DevUser friend code>.txt` (contents are only a six-digit color) | DevUser has a built-in colored tag and is using the mod client | DevUser's built-in tag color |

For example, create `TOHE-DATA/Tags/SPONSOR_TAGS/<DevUser friend code>.txt` containing only:

```text
33CCFF
```

This raw-color file must contain only a six-digit RGB hexadecimal color without `#`; it does not support gradients, is not interpreted as a structured player configuration, and does not make an ordinary player a sponsor. To configure a player's tag or permissions, use a structured file with fields such as `TagName:`, `TagColor:`, or `PermissionLevel:`; those fields determine its effect even when the file is in `SPONSOR_TAGS`.

After editing a `SPONSOR_TAGS` color file, run `/tags reload` in the lobby to refresh names, or host a room again. Built-in developer tags, including DevUser, continue to display according to the mod's built-in behavior.

## Add or remove tags in-game

The host enters:

```text
/addtag <player ID> <six-digit hexadecimal color> <tag text>
/deletetag <player ID>
```

For example, `/addtag 3 33CCFF Sample tag` adds a light-blue **fallback tag** to player ID 3. `/createtag` is the same as `/addtag`. The add command works in-game and in the lobby; the tag appears on the name in the lobby. The delete command works only in the lobby. The player must still be connected to the current room and have a friend code.

Write the color as six-digit RGB hexadecimal without `#`, for example `FF00AA`. If the color or arguments are invalid, the command shows usage information and does not save a tag. Using `/addtag` on the same player again replaces the old tag in `tags.txt`. `/deletetag` removes only the entry from `tags.txt`; it does not modify a per-player TXT file. If that file contains a valid `TagName`, it continues to take precedence for display.

## Edit the fallback tag file manually

After the first successful tag addition, `TOHE-DATA/tags.txt` appears in the game's working directory. This file is on the host's device and is not uploaded to other hosts. Each line is stored as “friend code=colored tag”, for example:

```text
sampleuser#1234=<color=#33CCFFFF>Sample tag </color>
otheruser#5678=<color=#FF00AAFF>Event host </color>
```

Only the first `=` after the friend code acts as the separator, so `=` characters in color markup and tag text are read correctly. After manual edits, the host can enter `/tags reload` to reload the file; when run in the lobby, it also refreshes the display immediately. The file is reloaded when hosting a room again as well. Deleting a line from the file and reloading removes that player's fallback tag; a tag in a per-player TXT file is unaffected. If the file does not exist, no one receives a fallback tag automatically.

`LocalPlayerTags.json` is no longer used, and its data is not migrated. Old Moderator/VIP lists and color directories are not migrated automatically, and existing files are not deleted automatically. Permissions and GM status from local files come only from per-player TXT files; `tags.txt` remains a cosmetic fallback and does not grant permissions.

Per-player TXT tags take precedence over cosmetic fallback tags in `tags.txt`. Built-in developer tags can still appear before them, and `SPONSOR_TAGS` can override built-in sponsor tag colors. Local tags are also hidden when “Hide all tags and text” is enabled.

## Relationship to EHR

The `tags.txt` command form and “friend code=tag” format are based on EHR. This mod splits on the first `=` so `<color=#...>` can still be loaded after hosting a room again. EHR private tags do not directly grant VIP, moderator, or admin commands, but a loaded tag makes the player trusted by EHR. That skips EHR's host-side RPC rate limit and prevents automatic kicks or bans in certain anti-cheat response modes. Detection may still block or report invalid behavior, and this does not grant an exemption from the official anti-cheat. TOHEE `tags.txt` does not grant these trust effects. See EHR's [trust check](https://github.com/Gurge44/EndlessHostRoles/blob/6ced0ff0880a4efd654c9d0734faf9c37f43ce5b/Modules/ExtendedPlayerControl.cs#L2440-L2455), [RPC rate limit](https://github.com/Gurge44/EndlessHostRoles/blob/6ced0ff0880a4efd654c9d0734faf9c37f43ce5b/Modules/RPC.cs#L294-L306), and [anti-cheat responses](https://github.com/Gurge44/EndlessHostRoles/blob/6ced0ff0880a4efd654c9d0734faf9c37f43ce5b/Modules/EAC.cs#L1059-L1109). TOHEE reads friend codes from the owners of currently connected players so stale player objects do not match the wrong tag.
